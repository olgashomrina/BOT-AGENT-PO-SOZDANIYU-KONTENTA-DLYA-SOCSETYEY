# Переезд бота с Timeweb Cloud на Beget

Инструкция описывает перенос **уже работающего в проде** бота с Timeweb Cloud
(сервер `147.45.175.189`) на Beget. Это не первый деплой — базовая установка
описана в `README-deploy.md`, а здесь только то, что специфично для переезда:
что нужно перенести, в каком порядке переключать и что сломается, если
порядок нарушить.

Читать сверху вниз и выполнять по порядку. Шаги, которые может сделать только
владелец (стоят денег или требуют входа в личные кабинеты), отмечены
**[владелец]**.

---

## Нужен именно VPS, а не обычный хостинг

На Beget есть и виртуальный хостинг, и VPS. Боту нужен **VPS**, и вот почему:

- Бот — это процесс, который работает круглосуточно (long polling: сам
  постоянно опрашивает Telegram). Виртуальный хостинг рассчитан на сайты,
  которые «просыпаются» на время запроса, и постоянно висящие процессы там
  либо запрещены правилами, либо будут убиваться.
- Нужен `systemd`, чтобы бот сам поднимался после падения и после
  перезагрузки сервера. Это требует root-прав, которых на хостинге нет.
- Бот поднимает свой веб-сервер на порту 8080 (API для сайта, см. Шаг 8) —
  на хостинге произвольный порт занять нельзя.

Конфигурация: **Ubuntu 22.04 LTS или новее, 1 vCPU, 1–2 ГБ RAM**, публичный
IP. Это тот же класс машины, что и на Timeweb — код и systemd-юнит переносятся
без изменений.

> Если позже захотите поднять распознавание речи на своём сервере
> (faster-whisper, см. `dengi.md`) — берите сразу 2 vCPU / 4 ГБ, на 1 ГБ оно
> не поместится.

---

## Что именно нужно перенести

Код прилетит из Git. Кроме кода на старом сервере живут четыре вещи, и три из
них нельзя потерять:

| Что | Где на сервере | Потеря означает |
|---|---|---|
| `.env` | `/opt/content-bot/.env` | не работает ничего: нет токена бота и ключа ИИ-прокси |
| `bot.db` | `/opt/content-bot/bot.db` | сброс белого списка, языков, каналов, примеров стиля, тем дайджеста и истории расходов |
| `site_media/` | `/opt/content-bot/site_media/` | пропадут фото карточек, которые сайт тянет через API |
| `logs/` | `/opt/content-bot/logs/` | только история диагностики, переносить не обязательно |

## Шаг 1 — Заказать VPS на Beget **[владелец]**

1. Личный кабинет Beget → раздел **VPS** → создать сервер.
2. ОС — **Ubuntu 22.04 LTS** (или новее), конфигурация минимальная
   (1 vCPU / 1–2 ГБ), публичный IP — обязательно.
3. Сохраните **IP-адрес** и **пароль root** (или загрузите свой SSH-ключ при
   создании — так удобнее и безопаснее).

**Старый сервер на Timeweb пока не отключайте и не удаляйте.** Он остаётся
рабочей копией на случай отката, и на нём лежат данные, которые мы будем
копировать. Отключить его — последний шаг (Шаг 10), не раньше чем через
несколько дней успешной работы на Beget.

---

## Шаг 2 — Подготовить сервер

Подключиться и поставить всё нужное (в PowerShell на своём компьютере,
`НОВЫЙ_IP` — адрес сервера Beget):

```bash
ssh root@НОВЫЙ_IP

apt update && apt upgrade -y
apt install -y python3 python3-venv python3-pip git
python3 --version   # должно быть 3.10 или новее
```

## Шаг 3 — Забрать код

```bash
git clone https://github.com/Lina-1979/BOT-AGENT-PO-SOZDANIYU-KONTENTA-DLYA-SOCSETYEY.git /opt/content-bot
cd /opt/content-bot
git checkout feature/mvp1-bot
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Ветка именно `feature/mvp1-bot` — это рабочая ветка прода, на неё же настроен
автодеплой (`.github/workflows/deploy.yml`).

## Шаг 4 — Перенести данные со старого сервера

Самый простой способ — скопировать напрямую с сервера на сервер. Выполняется
**на новом сервере (Beget)**, `147.45.175.189` — старый Timeweb:

```bash
cd /opt/content-bot
scp root@147.45.175.189:/opt/content-bot/.env   ./.env
scp root@147.45.175.189:/opt/content-bot/bot.db ./bot.db
scp -r root@147.45.175.189:/opt/content-bot/site_media ./
chmod 600 .env
```

`scp` спросит пароль root старого сервера. Так секреты идут напрямую между
серверами и не проходят через переписку и буфер обмена.

**Проверка, что данные доехали:**

```bash
ls -la /opt/content-bot/.env /opt/content-bot/bot.db
.venv/bin/python -c "import sqlite3; c=sqlite3.connect('bot.db'); print('пользователей в белом списке:', c.execute('SELECT COUNT(*) FROM whitelist').fetchone()[0])"
```

Число должно совпадать с тем, что было на Timeweb (как минимум не ноль).

**Если старый сервер уже недоступен** — `.env` придётся собрать заново по
`.env.example` (токен от @BotFather, ключ VseGPT из личного кабинета), а база
создастся пустой при первом запуске. Тогда после запуска нужно заново добавить
себя в белый список и выставить настройки. Проверьте отдельно, что
`AI_PROXY_API_KEY` — это ключ VseGPT (`sk-or-vv-…`), а не токен бота: на
локальной машине там как раз лежал токен бота, и из-за этого не работало
вообще ничего (см. `dengi.md`).

## Шаг 5 — Настроить systemd

Юнит переносится без изменений — путь `/opt/content-bot` тот же:

```bash
cp /opt/content-bot/deploy/systemd/content-bot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable content-bot
```

**Пока не запускайте.** Запуск — в следующем шаге, и порядок там важен.

---

## Шаг 6 — Переключение: сначала выключить старый, потом включить новый

⚠️ **Это единственный шаг, где ошибка порядка сразу видна пользователям.**
Telegram разрешает только одному процессу забирать сообщения по одному токену
бота. Если бот будет запущен одновременно на Timeweb и на Beget, Telegram
начнёт отдавать ошибку `409 Conflict`, и бот будет отвечать через раз или не
отвечать вовсе.

Поэтому строго по порядку:

1. **На старом сервере (Timeweb)** остановить бота:

   ```bash
   ssh root@147.45.175.189 "systemctl stop content-bot && systemctl disable content-bot"
   ```

   `disable` — чтобы старый бот не поднялся сам при перезагрузке того сервера
   и не начал конфликтовать с новым.

2. **На новом сервере (Beget)** запустить бота:

   ```bash
   systemctl start content-bot
   systemctl status content-bot
   ```

   Ожидаем `active (running)`. Свежие логи:

   ```bash
   journalctl -u content-bot -n 50 --no-pager
   ```

## Шаг 7 — Проверить, что бот живой

В Telegram, со своего реального аккаунта:

- [ ] `/start` — бот отвечает, меню на месте.
- [ ] Голосовое сообщение — приходит расшифровка (это же проверит, что ключ
      VseGPT правильный и на балансе есть деньги).
- [ ] Голосовое длиннее 3 минут — бот вежливо отказывается, ничего не тратя.
- [ ] Кнопка «Картинка от ИИ» — картинка приходит.
- [ ] `/costs` — приходит отчёт о расходах (если база переехала, там будут
      прежние цифры).

И проверка автоперезапуска — она же подтверждает, что systemd настроен:

```bash
systemctl kill content-bot
sleep 8
systemctl status content-bot   # снова active (running)
```

Полный смоук-тест — в `docs/manual-checklist.md`, раздел «Смоук-тест в проде».

## Шаг 8 — Перенастроить автодеплой на новый сервер **[владелец]**

Автодеплой (`.github/workflows/deploy.yml`) при пуше в `feature/mvp1-bot`
заходит по SSH на сервер из секрета `DEPLOY_HOST` и делает `git pull` +
`systemctl restart`. Пока секрет указывает на Timeweb, все будущие изменения
будут уезжать на **старый** сервер, а новый останется со старым кодом — тихо,
без ошибок.

1. На своём компьютере создать новый ключ для деплоя (или переиспользовать
   старый файл `deploy_content_bot`, если он сохранился):

   ```powershell
   ssh-keygen -t ed25519 -f $HOME\.ssh\deploy_beget -N '""'
   ```

2. Положить публичную часть на сервер Beget:

   ```powershell
   type $HOME\.ssh\deploy_beget.pub | ssh root@НОВЫЙ_IP "cat >> ~/.ssh/authorized_keys"
   ```

3. Проверить, что вход по ключу работает без пароля:

   ```powershell
   ssh -i $HOME\.ssh\deploy_beget root@НОВЫЙ_IP "echo ok"
   ```

4. В GitHub: репозиторий → **Settings** → **Secrets and variables** →
   **Actions** → обновить три секрета:

   - `DEPLOY_HOST` — новый IP сервера Beget;
   - `DEPLOY_USER` — `root`;
   - `DEPLOY_SSH_KEY` — **содержимое файла** `deploy_beget` (без `.pub`),
     целиком, вместе со строками `-----BEGIN…` и `-----END…`.

5. Проверка: сделать пустой коммит и убедиться, что деплой доехал именно на
   Beget:

   ```powershell
   git commit --allow-empty -m "chore: проверка автодеплоя на Beget"
   git push
   ```

   Через 1–2 минуты на сервере Beget:

   ```bash
   systemctl status content-bot   # время запуска должно обновиться
   ```

## Шаг 9 — API для сайта: новый адрес, новый сертификат **[владелец частично]**

Этот шаг нужен только если пилот синхронизации с сайтом используется
(см. `bot_site/README.md`). Адрес API привязан к IP сервера, поэтому после
переезда он меняется — и старый адрес перестанет отвечать.

1. На новом сервере поднять nginx с сертификатом. Новый домен — это IP через
   дефисы + `.sslip.io` (например, для `5.101.51.12` это
   `5-101-51-12.sslip.io`):

   ```bash
   apt install -y nginx certbot python3-certbot-nginx

   tee /etc/nginx/sites-available/content-bot-site-api > /dev/null <<'NGINX'
   server {
       listen 80;
       server_name НОВЫЙ-IP-ЧЕРЕЗ-ДЕФИСЫ.sslip.io;

       location / {
           proxy_pass http://127.0.0.1:8080;
           proxy_set_header Host $host;
       }
   }
   NGINX

   ln -s /etc/nginx/sites-available/content-bot-site-api /etc/nginx/sites-enabled/
   nginx -t
   systemctl reload nginx

   certbot --nginx -d НОВЫЙ-IP-ЧЕРЕЗ-ДЕФИСЫ.sslip.io
   ```

2. Проверка:

   ```bash
   curl https://НОВЫЙ-IP-ЧЕРЕЗ-ДЕФИСЫ.sslip.io/content/services/card_1
   ```

3. **На самом сайте** заменить старый адрес API на новый — в подключении
   скрипта:

   ```html
   <script src="site-content-loader.js" data-api-base="https://НОВЫЙ-IP-ЧЕРЕЗ-ДЕФИСЫ.sslip.io"></script>
   ```

   Пока это не сделано, карточка на сайте будет показывать старое содержимое
   или пустоту — сайт продолжит стучаться на выключенный Timeweb.

4. Если у Beget включён свой файрвол — открыть порты 80 и 443 в панели.

## Шаг 10 — Отключить Timeweb **[владелец]**

Не раньше, чем бот несколько дней стабильно проработал на Beget и вы проверили
всё из Шага 7. Пока старый сервер жив, откат занимает одну команду:

```bash
# откат: выключить новый, включить старый
ssh root@НОВЫЙ_IP "systemctl stop content-bot"
ssh root@147.45.175.189 "systemctl enable content-bot && systemctl start content-bot"
```

После отключения Timeweb этот путь отката пропадает — единственной копией
данных остаётся `bot.db` на Beget. Перед удалением старого сервера скачайте
`bot.db` и `.env` себе на компьютер в надёжное место.
