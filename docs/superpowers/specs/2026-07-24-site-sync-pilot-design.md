# Дизайн: пилот двусторонней синхронизации бота с сайтом (bot_site)

Дата: 2026-07-24
Статус: согласовано, готово к написанию плана реализации
Источники: обсуждение в чате, живой осмотр сайта `https://olgashomrina.github.io/my-lending-test/` и `services.html`, `bot/main.py`, `bot/handlers/refine.py`, `bot/storage/db.py`, `nadsroiki.md` (заметки о `MINI_APP_URL`)

## 0. Контекст и цель

У владелицы уже есть отдельный сайт (`my-lending-test`, репозиторий и вёрстка — отдельно, не в этом проекте, не трогаем HTML/CSS). Сайт — 9 статических HTML-страниц (главная, о себе, услуги, игра, погружение, ассистент, видео, faq, контакты), захостен на GitHub Pages, без единой строчки JS или API.

Цель: бот и сайт должны обмениваться контентом в обе стороны —
- бот генерирует текст/фото → «заливает» на нужный блок сайта;
- владелица открывает сайт из бота, находит нужный блок → «забирает» его текущее содержимое в бот для правки.

Это большая фича на весь сайт сразу; в этой спеке — **пилот на одном блоке одной страницы**, чтобы обкатать всю цепочку (инфраструктуру, API, push, pull, кнопку открытия сайта), прежде чем тиражировать на остальные страницы/карточки.

**Пилотный блок:** страница `services.html`, одна карточка услуг (например «Принятие тела») — текст + фото. Видео, остальные 8 карточек и остальные 8 страниц — вне пилота.

## 1. Инфраструктура

Сейчас бот работает через long polling (`bot/main.py`), без HTTP-сервера, без домена, без HTTPS. Добавляем:

- **API-сервер:** `aiohttp.web`-приложение в том же процессе бота (aiohttp уже стоит транзитивно через `aiogram`), запускается параллельно с polling в одном event loop. Только **чтение**: `GET /content/services/card_1`. Публичного эндпоинта на запись нет и не нужно — бот пишет в свою же БД напрямую в коде обработчика, без похода через HTTP к самому себе.
- **Домен/HTTPS:** своего домена нет → используем бесплатный `147-45-175-189.sslip.io` (резолвится на IP сервера), `nginx` как reverse proxy перед aiohttp, сертификат Let's Encrypt через certbot. Разовая серверная настройка.
- Причина, почему HTTPS обязателен: сайт на GitHub Pages отдаётся по HTTPS, браузер заблокирует запрос со страницы на обычный `http://` (mixed content).

## 2. Хранение данных

Новая таблица в существующей SQLite-базе бота:

```
site_content(
    page TEXT,             -- "services"
    block_id TEXT,         -- "card_1"
    text TEXT,
    photo_file_id TEXT,        -- Telegram file_id — источник правды, как и везде в проекте (см. refine.py:254-260)
    photo_static_path TEXT,    -- локальный путь на диске сервера, который отдаёт nginx как статику
    updated_at TEXT,
    PRIMARY KEY (page, block_id)
)
```

В пилоте — ровно одна строка: `page="services"`, `block_id="card_1"`.

**Почему две копии фото:** остальной бот хранит только Telegram `file_id` (осознанное решение, см. `refine.py`), но браузеру нужен обычный URL по HTTP. Поэтому при каждой «заливке» бот один раз скачивает файл по `file_id` и сохраняет копию на диск — эта копия и отдаётся сайту.

## 3. Три пользовательских сценария

### 3.1 Кнопка «МОЙ САЙТ»
Новая кнопка в меню бота, открывает `MINI_APP_URL` как Telegram Mini App (`InlineKeyboardButton(web_app=WebAppInfo(url=...))`). Просто живой просмотр сайта внутри Telegram — ничего не читает и не пишет.

### 3.2 Push: «Залить на сайт» (бот → сайт)
Появляется как ещё одна кнопка выбора публикации рядом с существующей «Опубликовать в канал» (Фаза 12, `bot/handlers/refine.py`) — после того как бот сгенерировал текст+фото. В пилоте пункт назначения один (карточка `card_1` на `services`), поэтому выбора страницы/блока пользователю не показываем — просто кнопка.

При нажатии:
1. Бот скачивает фото по `file_id` (Bot API `get_file` + download).
2. Сохраняет файл в статическую папку на сервере.
3. Записывает/обновляет строку `site_content` (текст, `file_id`, путь к статике, время).

Дальше при следующей загрузке `services.html` кем угодно в браузере — карточка уже показывает новый контент (без пересборки, без задержки).

### 3.3 Pull: «Забрать с сайта» (сайт → бот)
Новая команда/кнопка меню. Поскольку вариант один, сразу показывает текущие текст+фото карточки (то же самое, что видно на сайте — общий источник данных) и передаёт их в существующий флоу редактирования (`bot/handlers/refine.py`), как будто это только что сгенерированный контент. Пользователь правит как обычно, при необходимости снова «заливает».

### 3.4 Разовая правка `services.html`
Карточка-пилот получает фиксированные `id` на тексте и на `<img>`, плюс небольшой скрипт: при загрузке страницы делает `GET /content/services/card_1` и подставляет актуальные текст/фото в эти элементы. Остальная вёрстка страницы (и все остальные 8 страниц) не меняется.

## 4. Обработка ошибок

- API недоступен / сервер лежит → скрипт на сайте оставляет исходный (зашитый в HTML) текст карточки как есть — сайт не должен зависеть от бота для базовой работоспособности.
- Скачивание фото по `file_id` не удалось → push не завершается, пользователю в боте — понятная ошибка на русском, старое содержимое `site_content` не трогается (не затираем рабочую версию сайта половинчатым обновлением).

## 5. Тестирование

- Юнит-тесты на слой хранения (`site_content`: запись/чтение/upsert) — по образцу существующих тестов `bot/storage`.
- Тесты на API-эндпоинт (aiohttp test client): корректный JSON для существующего блока, 404 для несуществующего.
- Тесты на push/pull-обработчики — по образцу существующих тестов `refine.py`/`channel.py`.
- Ручная проверка владелицей: нажать «Залить на сайт», обновить `services.html` в реальном браузере, увидеть новый текст/фото; нажать «Забрать с сайта», увидеть то же содержимое в боте.

## 6. Явно вне пилота

- Остальные 8 страниц сайта и остальные карточки услуг — остаются статикой.
- Видео (пилот — только текст+фото).
- Публикация через GitHub API/коммиты в репозиторий сайта.
- Полноценный редактор внутри Mini App (выбор/правка прямо в браузере) — «забрать» и «залить» происходят через бота, не через интерфейс сайта.
- Аутентификация Telegram WebApp `initData` для страницы — сайт остаётся полностью публичным, как и сейчас.
