# Дизайн: тематический дайджест (новости / запросы / статьи / методики)

Дата: 2026-07-28
Статус: согласовано, готово к написанию плана реализации
Источники: обсуждение в чате, `Plan.md` (раздел 6, открытый вопрос «Дайджест тем по запросу», зафиксирован 2026-07-20), `bot/storage/users.py`, `bot/storage/db.py`, `requirements.txt`

## 0. Контекст и цель

Владелец (психолог по одной из аудиторий бота) хочет ежедневно видеть срез по заданной теме: что вирусится в новостях, что люди ищут в интернете, какие научные статьи вышли и набирают популярность, какие новые методики/приёмы появились. Та же механика должна работать для любой профессии пользователя бота (бухгалтер, строитель, дизайнер, учитель) — с выдачей 5–7 ссылок на источники.

Это первая реализация открытого вопроса из `Plan.md` §6 «Дайджест тем по запросу», ранее зафиксированного как пожелание владельца без технического решения. Ниже — конкретное решение.

Один общий конвейер на любую тему (не отдельная «ветка для психолога») — направления просто дают меньше или ничего, если профессии не подходят (например, «новые методики» для дизайнера может выдать пару новостей отрасли вместо научных статей).

**Уточнение от владельца (2026-07-28):** в боте уже есть кнопка-заглушка «Собрать дайджест свежих новостей» (`menu_news_digest_button`, добавлена как стаб в предыдущей сессии, см. `buttons.md`) — она должна стать реальной точкой входа в эту функцию, а не отдельная новая команда. Раздел 2 ниже переписан под этот сценарий.

## 1. Модель данных пользователя

Новое поле `digest_topic TEXT` в таблице `users`, по уже трижды использованному в проекте паттерну (`channel_id` — Фаза 12, `pending_media_*` — Фаза 13, `onboarding_shown` — Фаза 15):

```python
if "digest_topic" not in existing_columns:
    connection.execute("ALTER TABLE users ADD COLUMN digest_topic TEXT")
```

в `bot/storage/db.py`, плюс `set_digest_topic()`/`get_digest_topic()` в `bot/storage/users.py` (сигнатура — как `set_content_language`/`get_content_language`).

Отсутствие темы (новый пользователь ещё не настраивал дайджест) — `None`, автоматическая ежедневная рассылка пользователю в этом состоянии не отправляется (нечего собирать), только явное приглашение настроить.

## 2. Команды и UX

Никаких новых слэш-команд — вся функция строится вокруг уже существующей кнопки главного меню (кнопка `menu_news_digest_button` = «Собрать дайджест свежих новостей», callback `CALLBACK_NEWS_DIGEST`, сейчас — заглушка `bot/handlers/start.py:120-129`). Правится существующий обработчик `on_menu_news_digest`, новых команд не добавляется — согласовано с владельцем: одна точка входа вместо двух разных (кнопка + команда).

Сценарий нажатия **«Собрать дайджест свежих новостей»**:
- Если у пользователя уже есть сохранённая `digest_topic` → сразу собирается и присылается дайджест по этой теме (см. раздел 5), а следом — сообщение с инлайн-кнопкой **«Написать тему»** (сменить тему на другую).
- Если сохранённой темы ещё нет → дайджест не собирается, сразу показывается сообщение-приглашение с инлайн-кнопкой **«Напиши интересующую тему»** (новый callback `menu:digest_set_topic`, новый локализационный ключ `menu_digest_write_topic_button`).

Нажатие кнопки **«Напиши интересующую тему»**:
- Бот отправляет сообщение с `ForceReply(input_field_placeholder=...)` — у пользователя рядом с сообщением сразу открывается редактируемое поле ввода (то самое «выпадающее окно»), не нужно самому нажимать «Ответить».
- Переводит пользователя в новое FSM-состояние `DigestStates.waiting_for_topic` (по образцу `PhotoGenStates.waiting_for_description`, `bot/handlers/start.py:42-43`).
- Следующее текстовое сообщение пользователя ловится хендлером на этом состоянии: сохраняет тему (`set_digest_topic(db_path, telegram_id, topic)` — становится новой темой по умолчанию и для будущих автоматических ежедневных рассылок), сбрасывает состояние, вызывает `build_digest(topic)` и присылает результат.

Автоматическая ежедневная отправка — всем пользователям с непустым `digest_topic`, в одно и то же время для всех (09:00 МСК на старте, значение — константа в конфиге, не per-user настройка). Это отдельный, не завязанный на кнопку механизм (раздел 4).

Whitelist/лимит: и нажатие кнопки, и ввод темы в `ForceReply` идут через `callback_query`/обычный `message`-поток — используется тот же `_check_whitelist_or_reply`, что уже стоит на `on_menu_photo_gen`/`on_menu_capabilities` (`bot/handlers/start.py`). Автоматическая ежедневная рассылка **не проходит через middleware** (не инициирована входящим сообщением) — рассылка сама явно проверяет вайтлист (`is_whitelisted`) перед отправкой каждому пользователю, по аналогии с тем, как коллбэки в `bot/handlers/site.py` вручную дублируют эту проверку в обход мидлваров.

## 3. Источники данных по направлениям

| № | Направление | Источник (MVP) | Статус |
|---|---|---|---|
| 1 | Вирусные новости | Google News RSS (`https://news.google.com/rss/search?q=<тема>&hl=ru&gl=RU`) | Реализуется сразу |
| 2 | Поисковые запросы | Yandex Wordstat API | **Отложено** — доступ выдаётся Яндексом по заявке, срок неизвестен; пункт добавляется отдельной фазой после одобрения |
| 3 | Научные статьи | Semantic Scholar API (`/graph/v1/paper/search`, сортировка по `citationCount` + фильтр по свежести) + PubMed E-utilities для медицинских/психологических тем | Реализуется сразу |
| 4 | Новые методики | Не отдельный источник — синтез через `ai_gateway.generate_text()` поверх результатов направлений 1 и 3 | Реализуется сразу |

Все источники MVP — официальные и бесплатные, без ключа (Google News RSS, PubMed E-utilities) либо с бесплатным ключом без коммерческих ограничений (Semantic Scholar — заявка на повышенный лимит опциональна). Исследование подтвердило: pytrends/неофициальный Google Trends нежизнеспособен (архивирован, блокируется на первом же запросе) — не рассматривается вообще ни как временное, ни как постоянное решение.

## 4. Архитектура сбора

Новый `bot/services/digest.py` — по одной чистой async-функции на источник, без побочных эффектов, легко мокается в тестах (как `input_processor.py` мокает `trafilatura`):

- `fetch_viral_news(topic: str) -> list[DigestItem]` — парсинг Google News RSS через `feedparser`.
- `fetch_scientific_papers(topic: str) -> list[DigestItem]` — HTTP-вызов Semantic Scholar через уже используемый в проекте `httpx`.
- `synthesize_new_methods(news: list[DigestItem], papers: list[DigestItem]) -> str` — один вызов `ai_gateway.generate_text()` с промптом-экстрактором.
- `build_digest(topic: str) -> DigestResult` — оркестрирует три функции выше (`asyncio.gather`, каждая обёрнута в try/except — сбой одного источника не должен ронять остальные, см. раздел 7), собирает итоговые 5–7 ссылок.

`DigestItem` — простой `dataclass` (заголовок, ссылка, направление-источник).

Новый `bot/services/digest_scheduler.py` — `AsyncIOScheduler` (APScheduler) с одной ежедневной задачей, регистрируется в `bot/main.py` при старте наравне с Dispatcher (внутри того же процесса — без нового systemd-юнита, без второго деплой-артефакта). Задача проходит по всем пользователям с непустым `digest_topic`, для каждого — вайтлист-проверка → `build_digest` → отправка сообщением.

Изменения в существующих файлах (не новые модули, а правки под сценарий раздела 2):
- `bot/handlers/start.py` — `on_menu_news_digest` переписывается (вместо заглушки: ветвление «есть тема / нет темы», см. раздел 2); добавляется `DigestStates` (`StatesGroup`, рядом с `PhotoGenStates`) и обработчик `on_digest_topic_input` по образцу `on_photo_gen_description`.
- `bot/keyboards/start.py` — новая функция `build_digest_topic_keyboard(lang: str, has_saved_topic: bool) -> InlineKeyboardMarkup` (одна кнопка, текст зависит от `has_saved_topic`: «Напиши интересующую тему» либо «Написать тему»), новый `CALLBACK_DIGEST_SET_TOPIC = "menu:digest_set_topic"`.

## 5. Формат вывода

Одно сообщение (или несколько, если превышает лимит Telegram на длину — та же логика обрезки/разбиения, что уже применяется к caption в `refine.py`), с заголовком «Дайджест по теме «{тема}» за {дата}», далее по направлениям (только те, что дали результат):

```
📰 В новостях
1. <заголовок> — <ссылка>
...

🔬 Научные статьи
1. <заголовок> — <ссылка>
...

💡 Новые методики
<1–2 предложения синтеза от ИИ, со ссылками на статьи/новости, из которых это извлечено>
```

## 6. Обработка ошибок

Каждый источник в `build_digest` — независимый try/except:
- Источник недоступен/вернул пусто → он просто отсутствует в итоговом сообщении, без падения остальных.
- Все источники пусты одновременно → пользователь получает дружелюбное сообщение «по теме «{тема}» сегодня ничего не нашлось» вместо пустого дайджеста (тот же принцип, что и в таксономии ошибок раздела 5 `Plan.md` — никогда не показывать техническую ошибку/пустоту без объяснения).
- Ошибки AI Gateway на шаге синтеза методик — используется существующая таблица `_AI_ERROR_KEYS`/типизированные исключения (`Plan.md` раздел 5.2); при ошибке синтеза направление «Новые методики» просто пропускается, остальные направления всё равно отправляются.

Существующий `menu_news_digest_hint` (текст-заглушка «пока в разработке») удаляется — стаб больше не нужен, обработчик больше не показывает эту строку.

Новые ключи (все 4 языка, как того требует `test_all_locales_have_identical_keys`): `menu_digest_write_topic_button` («Напиши интересующую тему»), `menu_digest_change_topic_button` («Написать тему» — та же кнопка, другой текст для случая «тема уже есть»), `digest_topic_input_placeholder` (плейсхолдер `ForceReply`, например «Например: психология»), `digest_topic_saved` (подтверждение сохранения темы), `digest_section_news`, `digest_section_papers`, `digest_section_methods`, `digest_empty_result` (все источники пусты).

## 8. Тестирование

- `tests/test_services_digest.py` — юнит-тесты каждой функции `digest.py` с моками HTTP (`respx`, как в `test_ai_gateway.py`/`test_input_processor_link.py`): успех, пустой ответ, недоступный источник; `build_digest` — сбой одного источника не блокирует остальные (ключевой сценарий).
- `tests/test_storage_users.py` — расширяется `get/set_digest_topic`, миграция на «боевой» схеме без `digest_topic` (тот же паттерн, что уже трижды использован).
- `tests/test_handlers_start.py` (расширяется, обработчики живут в `start.py`) — нажатие «Собрать дайджест свежих новостей» без сохранённой темы показывает приглашение с кнопкой «Напиши интересующую тему»; с уже сохранённой темой — сразу присылает дайджест и кнопку «Написать тему»; нажатие «Напиши интересующую тему»/«Написать тему» переводит в `DigestStates.waiting_for_topic` и отправляет `ForceReply`; текстовый ответ в этом состоянии сохраняет тему и присылает дайджест; не-вайтлистнутый пользователь получает отказ на каждом из этих шагов (тот же паттерн, что уже проверяется для `on_menu_photo_gen`).
- Планировщик (`digest_scheduler.py`) — тест на то, что задача регистрируется и вызывает `build_digest`/отправку для каждого пользователя с `digest_topic`, вайтлист-фильтрация проверяется отдельно (мок `is_whitelisted`).
- Ручная проверка владельцем: нажать «Собрать дайджест свежих новостей» → «Напиши интересующую тему» → ввести «психология» → получить дайджест; нажать кнопку повторно — дайджест должен собраться сразу по сохранённой теме без повторного ввода; дождаться автоматической рассылки на следующий день.

## 9. Новые зависимости и стоимость

`requirements.txt` пополняется: `feedparser` (парсинг Google News RSS), `apscheduler` (планировщик задач в процессе).

$0 новых расходов на источники данных (все бесплатные/официальные). Единственный новый повторяющийся расход — несколько дополнительных вызовов `ai_gateway.generate_text()` в день на активного пользователя (шаг синтеза «новых методик») — тот же AI Gateway и биллинг vsegpt.ru, что бот уже использует.

## 10. Явно вне объёма

- Направление «поисковые запросы» (Yandex Wordstat API) — доступ ожидает одобрения Яндекса, добавляется отдельной фазой/задачей после получения ключа, не блокирует остальной функционал (тот же подход, что и с Instagram auto-publish в `Plan.md` Фаза 12).
- Индивидуальное время ежедневной рассылки на пользователя — не в MVP, время фиксировано и одинаково для всех.
- Дайджест на языках, отличных от русского (EN/VI/ZH) — источники (особенно Wordstat в будущем) заточены под русскоязычный контент; для не-RU интерфейса функция может быть временно скрыта/недоступна, явное решение — на этапе реализации, не заблокировано этой спекой.
- Модерация/фактчекинг содержимого дайджеста перед отправкой — не входит, как и для остального генерируемого контента бота (см. `Plan.md` раздел 6, «минимальный объём модерации»).
